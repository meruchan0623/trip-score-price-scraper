# HK/RU scheduled competitor promotion report

The 03:00 Mode2 schedule now collects only `hk,ru`. It runs five workers with normal delay and a fresh frozen Google target/session, then accepts only a merged `*_trip_mode2_daily_2site.xlsx` having exactly HK/RU sheets and every frozen target ID exactly once per sheet. A legacy six-site done marker cannot suppress this scope; six-site workbooks are immutable and are accepted only as a previous-natural-day baseline.

`trip_mode2_direct_delivery.py` invokes `scripts/trip_competitor_promo_report.py` with the run-local frozen target snapshot. It delivers the raw two-site workbook and a separate report XLSX through `trip_deliver.py`, retaining idempotency receipts; it writes no completion marker after a send failure. New scheduled report attachments are named `Trip_Mode2_HK-RU_竞品促销报告_YYYYMMDD-HHMM.xlsx`: the timestamp comes from the native `YYMMDD-HHMM_trip_mode2_daily_2site.xlsx` collection-start name, otherwise valid `cron_tick`, otherwise the source file timestamp (Shanghai), never a retry clock. The renderer still writes `report.xlsx`, which is renamed once before delivery; pre-existing generic reports and successful receipts are left untouched. Missing baselines produce a pending report rather than treating rows as additions. At most two Telegram-safe text messages carry date, baseline, pending vendor counts, and direct event comparisons.

The report module never collects or modifies inputs, cron, or sends messages. Every non-TSIM frozen target vendor column is included; ambiguous target identity pairings are quarantined. HK/RU output sheets preserve every raw row and original column, plus destination, quality reasons, and parsed non-50 discount. Detail sheets retain competitor and TSIM IDs.

Only explicit `%`/`％` values in `[0,100]` parse; `折` does not. Exact 50% is excluded, while only-50% becomes zero. Empty promotion labels and any nonempty failure note are pending; empty pending sets are discarded. Joined live vendors such as `BC/TGT` union their split frozen mappings and deduplicate identical destination/TSIM pairs. Messages start with generated report-date, baseline, and pending summary, then render each event as `目的地｜站点｜竞品 原折扣→新折扣｜TSIM 值 <|>|= 竞品 新折扣`; when TSIM is unknown they render `TSIM 待确认` with no comparison. Synchronization requires two distinct sites. Report cells are all saved as text; audit records thresholds, unique-input counts, pending vendor breakdown, and 50%-only exclusions.
